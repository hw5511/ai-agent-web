# Session 12 — 회원 시스템 (Supabase Auth) · 슬라이드 목차

> **회차 한 줄 요약**: Supabase Auth로 회원가입·로그인·로그아웃을 만들고, "내 데이터만 보이게" 분리한다.
> **회차 끝 학생 상태**: 회원만 글을 쓰고, 자기 글만 볼 수 있는 페이지 완성.
> **표현 원칙**: 회원 시스템 / 로그인 / 로그인 상태 (인증·인가·토큰·백엔드·풀스택 단어 사용 금지). RLS 약자만 허용.

- **goal**: 오늘 만들 것 — 회원만 들어올 수 있는 페이지, 한 줄로 소개한다.

  - 11주차 "모두 함께 보는 방명록" → 12주차 "내 글만 보이는 방명록"

- **강사 노트**: "백엔드"라는 단어는 절대 쓰지 말 것. "회원 시스템"으로 통일. 학생이 위협감 느끼지 않도록 "Claude Code가 거의 다 만들어준다" 강조.

### 슬라이드 2 — 오늘의 학습 목표
- **유형**: 학습목표
- **goal**: 회원가입·로그인·로그아웃 + "내 데이터만 보기"의 4가지를 직접 구현할 수 있게 된다.
- **핵심 토픽**:
  - [목표 1] 회원가입 폼 만들기 (이메일 + 비밀번호)
  - [목표 2] 로그인 / 로그아웃 동작시키기
  - [목표 3] 로그인 상태를 화면에 표시하기 ("OOO님 환영합니다")
  - [목표 4] "내가 쓴 글만" 보이게 만들기 (user_id + RLS)
  - 회차 끝 인증 미션: 11주 방명록을 내 글만 보이게 변신
- **시각 요소**:
  - 4단계 체크리스트 카드 (각 단계마다 아이콘)
  - 하단 "오늘 안 다루는 것" 박스: SMS 인증, 비밀번호 찾기 (다음 기회)
- **강사 노트**: 4개 목표 중 1·2번은 거의 자동, 3·4번에서 집중 필요. 학생에게 "오늘 안에 다 됩니다"라고 안심시키기.

### 슬라이드 3 — 개념 ① 왜 회원 시스템이 필요한가
- **유형**: 개념
- **goal**: "모두 공유 데이터"와 "내 데이터"의 차이를 직관적으로 이해한다.
- **핵심 토픽**:
  - 11주차까지: 모두가 같은 방명록을 보고 씀 (익명 게시판 같은 느낌)
  - 12주차부터: 내 일기, 내 메모, 내 쇼핑 목록처럼 "나만 보는 데이터"
  - 일상 예시: 카카오톡 = 내 채팅방만 / 인스타 = 내 게시물만 편집 가능
  - 책임과 프라이버시: 누가 썼는지 알 수 있어야 함
  - 결론: 진짜 서비스가 되려면 "누가 누군지" 식별이 필요하다
- **시각 요소**:
  - 좌우 비교 일러스트: [11주 공용 게시판] ↔ [12주 개인 일기장]
  - 익숙한 앱 로고 4개 (카톡·인스타·노션·메모앱) — 모두 회원 시스템
  - 화살표 그래픽: "공유 DB → 개인화 DB"
- **강사 노트**: 어렵게 설명하지 말 것. "내 노션이 남에게 안 보이는 이유" 한 마디면 충분.

### 슬라이드 4 — 개념 ② Supabase Auth 한눈에
- **유형**: 개념
- **goal**: 복잡한 회원 시스템을 Supabase가 통째로 대신 만들어준다는 사실을 안다.
- **핵심 토픽**:
  - Supabase Auth = "회원 시스템 통째로 제공" 서비스
  - 이메일+비밀번호 / 구글 로그인 / 깃허브 로그인 — 다 기본 제공
  - 가입하면 Supabase가 자동으로 "회원 명단" 테이블에 추가
  - 로그인 상태도 브라우저에 알아서 저장 (창 닫아도 유지)
  - 우리가 직접 짜야 하는 건 "폼 UI"와 "버튼 클릭" 정도
- **시각 요소**:
  - 가운데 큰 박스 "Supabase Auth" + 들어오는 화살표 3개 (이메일·구글·깃허브)
  - 나가는 화살표: "회원 명단 자동 관리" / "로그인 상태 자동 유지"
  - 비교 표: 직접 만들면 (DB·암호화·세션·메일발송 …) vs Supabase (한 줄 호출)
- **강사 노트**: "토큰" 단어 금지. "로그인 상태"로만 표현. 학생이 "이걸 다 해준다고요?" 반응 나오면 OK.

### 슬라이드 5 — 개념 ③ "내 데이터만 보기"의 비밀: user_id + RLS
- **유형**: 개념
- **goal**: 각 행에 "주인 표시(user_id)"를 달고, RLS로 남의 데이터 접근을 막는 원리를 이해한다.
- **핵심 토픽**:
  - 모든 데이터(글·메모·일기)에 "주인 표시" 한 칸 추가 → 컬럼명 `user_id`
  - 글을 저장할 때: "이 글의 주인 = 지금 로그인한 나"로 자동 기록
  - 글을 불러올 때: "주인이 나인 것만" 골라서 가져옴
  - RLS (Row Level Security) = "내 데이터 보호 규칙"
  - Supabase 화면에서 클릭 몇 번으로 규칙 켜기 가능
- **시각 요소**:
  - 표 일러스트: posts 테이블에 user_id 컬럼 강조 (색칠)
  - 자물쇠 아이콘이 각 행마다 달림 → 다른 사용자가 접근 시 X 표시
  - RLS 정책 예시 박스: "auth.uid() = user_id 인 행만 보임"
- **강사 노트**: 학생에게 직접 SQL 쓰라고 하지 말 것. "Supabase UI에서 토글 켜는 정도"라고 안심.

### 슬라이드 6 — 실습 ① 회원가입 폼 만들기
- **유형**: 실습
- **goal**: 이메일·비밀번호 입력 폼을 만들고 Supabase signUp으로 연동한다.
- **핵심 토픽**:
  - 화면 만들기: 이메일 input + 비밀번호 input + "가입하기" 버튼
  - Claude Code에게 줄 프롬프트:
    > "회원가입 폼(이메일·비번)을 만들고 Supabase Auth signUp으로 연동해줘."
  - 동작 확인: 가입 후 Supabase 대시보드 → Authentication 탭에 내 이메일 추가됐는지
  - 성공·실패 메시지 띄우기 (alert 정도면 OK)
  - 흔한 함정: 비밀번호 최소 6자 / 이메일 형식 오류
- **시각 요소**:
  - 좌측: 완성된 회원가입 폼 스크린샷 목업
  - 우측: Supabase 대시보드 "Users" 목록에 이메일이 추가된 모습
  - 하단 코드박스 1줄:
    ```js
    await supabase.auth.signUp({ email, password })
    ```
- **강사 노트**: 학생이 가입할 이메일은 본인 진짜 이메일이 아니어도 됨 (test1@test.com 등). 단, Supabase 프로젝트 설정에서 "이메일 인증 OFF" 켜둘 것.

### 슬라이드 7 — 실습 ② 로그인 · 로그아웃 + 로그인 상태 표시
- **유형**: 실습
- **goal**: 로그인·로그아웃 버튼을 만들고, 화면 상단에 "OOO님" 표시까지 완성한다.
- **핵심 토픽**:
  - 로그인 폼: 회원가입과 거의 같지만 호출이 `signInWithPassword`
  - 로그아웃 버튼: `signOut()` 한 줄
  - 로그인 상태 감지: `onAuthStateChange` — 로그인/로그아웃 즉시 화면 갱신
  - 화면 상단: 로그인 전 → "로그인" 버튼 / 로그인 후 → "OOO님, 로그아웃"
  - 새로고침해도 로그인 유지되는지 확인 (브라우저가 자동 기억)
  - Claude Code 프롬프트:
    > "로그인 폼·로그아웃 버튼 추가해줘. 로그인 상태가 화면 상단에 표시되도록."
- **시각 요소**:
  - 상태 전환 다이어그램: [비로그인] ─ 로그인 ─> [로그인됨] ─ 로그아웃 ─> [비로그인]
  - 헤더 영역 비교 목업 2개 (로그인 전 / 후)
  - 코드박스:
    ```js
    supabase.auth.signInWithPassword({ email, password })
    supabase.auth.signOut()
    ```
- **강사 노트**: 로그인 직후 화면이 안 바뀌면 99% `onAuthStateChange` 누락. Claude Code에게 "로그인 즉시 화면 갱신되게"라고 한 줄 추가 요청.

### 슬라이드 8 — 실습 ③ 11주 방명록을 "내 글만 보이게" 변신
- **유형**: 실습
- **goal**: 기존 방명록에 user_id를 붙이고 RLS를 켜서, 로그인한 본인 글만 보이고 쓸 수 있게 만든다.
- **핵심 토픽**:
  - 1단계: posts 테이블에 `user_id` 컬럼 추가 (Supabase UI 클릭)
  - 2단계: 글 작성 코드 수정 → 저장 시 `user_id: currentUser.id` 자동 첨부
  - 3단계: 글 조회 코드 수정 → `.eq('user_id', currentUser.id)` 또는 RLS에 맡기기
  - 4단계: Supabase에서 RLS 켜기 + 정책 추가 ("auth.uid() = user_id")
  - 5단계: 두 계정으로 테스트 — A가 쓴 글이 B에게 안 보여야 성공
  - Claude Code 프롬프트:
    > "11주 방명록을 변경해서 로그인한 사용자 본인 글만 보이고 쓸 수 있도록 해줘."
- **시각 요소**:
  - 5단계 플로우 (1·2·3·4·5 번호 박스)
  - Before / After 화면 비교: [공용 글 5개] → [내 글 2개만]
  - 두 브라우저 창 (계정 A · 계정 B) 비교 스크린샷 목업
- **강사 노트**: 가장 어려운 슬라이드. RLS를 안 켜면 코드만으로도 동작은 하지만 "진짜 보호"는 아님을 한 마디 짚어줄 것. 두 계정으로 꼭 검증.

### 슬라이드 9 — 핵심 정리: 이제 진짜 서비스 같다
- **유형**: 정리
- **goal**: 오늘 얻은 4가지 능력을 복기하고, 다음 주(13회차 도메인) 예고로 마무리한다.
- **핵심 토픽**:
  - 오늘 새로 생긴 능력:
    1. 회원가입·로그인·로그아웃 구현
    2. 로그인 상태를 화면에 반영
    3. 데이터에 "주인 표시(user_id)" 붙이기
    4. RLS로 내 데이터 지키기
  - 한 줄 회고: "이제 누가 봐도 진짜 서비스다"
  - 응용 아이디어: 개인 일기장 / 비밀 메모장 / 내 쇼핑 위시리스트
  - 다음 주 예고 (Session 13): 내 서비스에 **도메인 연결** — "내 사이트 주소.com"
  - 과제(선택): 오늘 만든 방명록을 "비밀 일기장"으로 한 줄 리뉴얼
- **시각 요소**:
  - 회차 끝 화면 스크린샷 목업 (로그인된 상태, 내 글 목록)
  - 4칸 카드: 오늘 얻은 능력 4가지 아이콘
  - 우측 하단 "다음 주 예고" 박스 — 도메인 아이콘 + 13주차 타이틀
- **강사 노트**: 학생들 박수받기 좋은 회차. "백엔드 단어 한 번도 안 썼는데 회원 시스템 완성한 거예요" 한 마디로 자신감 부여.
